# Phase 3 — Трекинг: контекст и границы

**Дата:** 2026-05-14  
**Зависимость:** Phase 2 (чекаут и заказ) — выполнена; базовая машина статусов и UI списка/детали заказа уже есть.

## Что входит в «трекинг» в этом репозитории

- **Покупательский контур:** страницы `OrdersPage` / `OrderDetailPage`, данные только из **`GET /api/order/my-orders`** и **`GET /api/order/my-orders/:id`** (через gateway).
- **Истина о прогрессе заказа:** поле **`order.status`** (enum в `services/order-service/src/models/Order.ts`). Отдельных полей «manufacturing», «fulfillment stage», трек-номера в модели **нет**.
- **Тип линии заказа** (влияет на *ожидаемую* историю «изготовление vs только отгрузка»): только из **`order.items[].type`** — `jewelry` (готовое изделие), `bespoke` (комплект на заказ), `diamond` (камень), `setting` (оправа, если появится в данных).

## Границы по сценариям (продукт vs код сегодня)

| Сценарий | Что означает «трекинг» для пользователя | Что реально отражает API сегодня |
|----------|----------------------------------------|----------------------------------|
| **Готовое украшение (`jewelry`)** | Оплата → подготовка/отгрузка → доставка | Те же **`OrderStatus`**, что и для остальных; отдельного статуса «на складе / в производстве» **нет**. |
| **Bespoke (`bespoke`)** | Оплата → изготовление/сборка → отгрузка → доставка | После оплаты — **`CONFIRMED`** до ручного/операционного перевода в **`SHIPPED`** / **`DELIVERED`**; **нет** дискретного «в изготовлении» в БД. |
| **Только бриллиант (`diamond`)** | Оплата → отгрузка камня → доставка | Аналогично: только общий enum статусов заказа. |

**Вывод для планов:** UX может давать *контекстные подсказки* по `items[].type`, но **не** имитировать подэтапы, которых нет в `order.status`, без изменения схемы/сервиса (вне Phase 3 minimal slice, если не появится явное решение).

## Зафиксированные решения (D-03 — исполнение Phase 3)

| ID | Решение | Обоснование |
|----|---------|-------------|
| **D-03-01** | Источник истины для отображаемых этапов — **`OrderStatus`** из API; новые именованные этапы в UI **без** соответствующего значения в API **запрещены**. | TRK-02: доверие и chargeback-риск при «лишних» шагах. |
| **D-03-02** | Текст «изготовление / только логистика» — только как **пояснение к типу позиции** и/или к текущему **`order.status`**, с явной формулировкой, где это ожидание, а не отдельный сигнал бэкенда. | Нет поля manufacturing в модели. |
| **D-03-03** | Линейка шагов (timeline) строится **только** из допустимых переходов `PENDING` → … → терминал (`DELIVERED` / `CANCELLED`); визуально «текущий» шаг определяется **только** фактическим `order.status`. | TRK-01 при минимальном объёме. |
| **D-03-04** | Статические фразы вроде «3–5 рабочих дней» не должны противоречить тому, что пользователь видит в статусе; их приводим в согласование с типом заказа и статусом или ослабляем до нейтральной формулировки. | TRK-02. |

## Отложено (не Phase 3 без нового обсуждения)

- Трекинг-номер перевозчика и интеграция ТК.
- Push/e-mail уведомления по смене статуса (см. notification-service — отдельная фаза/задача).
