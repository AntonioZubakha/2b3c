# Безопасность LGDX: политика и честный отчёт

**Версия документа:** 3.0  
**Последнее обновление:** март 2026  
**Статус:** единый источник правды по безопасности (объединяет бывшие `10_SECURITY.md`, `11_Security_Completion_Report.md`, `SECURITY_AUDIT.md`).

Этот файл совмещает **политику** (что задумано и как должно быть) и **оценку** (что можно доказать кодом/конфигом, где остаются риски). Формат намеренно **состязательный**: обвинение → защита → вердикт.

---

## Краткий вердикт

**Производственный контур (Docker Swarm, `docker-compose.prod.secure.final.yml`, Nginx, секреты в Swarm, приложение с Helmet/CSP, Stripe webhook verification) по уровню зрелости ближе к «серьёзный коммерческий SaaS», чем к «набросок».**  
При этом **«100% безопасности» не существует**: остаются операционные риски (локальный `.env`, бэкапы без шифрования, SPOF по Mongo/узлу), зрелость CI и регулярность проверок восстановления.

| Критерий | Оценка (субъективно) | Комментарий |
|----------|---------------------|-------------|
| Конфиденциальность секретов в prod | Хорошо | Docker Secrets, `*_FILE`, образы без секретов |
| Целостность и оплаты (Stripe) | Хорошо | Подпись webhook, секреты не в логах |
| Доступность и наблюдаемость | Средне-плюс | Стек мониторинга есть; часть алертов и сценариев улучшалась со временем |
| Устойчивость к компрометации бэкапов/носителей | Ниже среднего | Дампы без шифрования at rest в сервисе |
| Доказуемость соответствия (ISO/SOC2) | Не заявляется | Нужны отдельные процессы и артефакты |

## I. Обвинение (прокурор): слабые места и риски

1. **Локальный `.env` с реальными секретами**  
   В корне репозитория на машине разработчика часто лежит `.env`. В git он не должен попадать (`.gitignore`). Риск не в истории git (аудит 2026-03: `.env` в истории не обнаруживался), а в **случайном коммите, архиве, бэкапе папки, скриншоте**.  
   *Требование:* не полагаться на память — pre-commit, `.env.example` без секретов.

2. **Бэкапы Mongo без шифрования**  
   `backup-service` пишет `mongodump` в volume. Компрометация диска/копии бэкапа ≈ компрометация БД.  
   *Смягчение:* шифрование томов на хосте, отдельный ключ из секрета, оффлайн-копии с контролем доступа.

3. **Grafana и панели мониторинга**  
   Дефолт `admin` в compose — **риск только если не задан `GRAFANA_ADMIN_PASSWORD`**. Доступ по HTTPS к `/grafana/` без дополнительного слоя (IP allowlist, SSO) — поверхностная защита одним паролем.

4. **Публичные порты мониторинга**  
   Prometheus/Grafana/Loki на опубликованных портах на хосте (как в доках) — **увеличивают поверхность**, если firewall не строгий. Это не баг приложения, а **операционная** зона ответственности.

5. **FTP и legacy-потоки**  
   FTP по определению слабее SFTP; при этом у вас есть rate limit и изоляция — снижает злоупотребление, но не устраняет класс протокола.

6. **Один узел / одна реплика БД**  
   Типичный SPOF: падение ноды или повреждение volume — это про **авailability** и восстановление, не только «взлом».

7. **CI/CD**  
   В GitHub Actions тестовые сервисы с простыми паролями допустимы **только** в изолированном CI; важно не смешивать с prod-секретами. Пайплайн местами допускает «нет скрипта — продолжаем» — снижает барьер перед регрессией.

8. **Маркетинговый тезис «100%»**  
   Документ с галочками «всё выполнено» полезен как чеклист, но **не является аудитом** и не заменяет penetration test и регулярный `npm audit`/патчи.

## II. Защита (адвокат): что реально сделано сильно

1. **Секреты в production**  
   В боевом compose секреты через Docker Swarm, передача в приложения через файлы (`*_FILE`), а не через переменные в YAML для чувствительных значений.

2. **Край и приложение**  
   Nginx: TLS, HSTS, заголовки, зоны rate limit (в т.ч. login/register после доработок). Сервер: Helmet, CSP с режимом enforce в prod, rate limiting, CSRF для подходящих маршрутов.

3. **Аутентификация**  
   JWT, Redis для revocation, HttpOnly cookie, `COOKIE_SECURE=true` в prod.

4. **Платежи**  
   Stripe webhook через `constructEvent`, секрет из хранилища секретов.

5. **Загрузки и парсинг**  
   Лимиты размера, тесты на zip-bomb, multipart, SSRF — в кодовой базе есть целенаправленные security-тесты (`server/src/tests/security/`).

6. **Инциденты в логах (исправлено в ходе аудита)**  
   Убрано логирование verification token/code в открытом виде; не логируются пути к секретам в prod там, где это исправляли.

7. **Контейнеры**  
   Non-root, `read_only`, ограничения capabilities в prod-конфигурациях — соответствует здравому hardening.

8. **Мониторинг и алерты**  
   Prometheus/Alertmanager/Loki, маршрутизация в Telegram; правила по сервисам, бэкапам, SSL (развитие по времени — см. `info/18_Monitoring.md`).

## III. Судья: выводы и приоритеты

**Не обвинять продукт в «небезопасности» целиком** — по совокупности контролей это **осознанная** архитектура.  
**Не успокаиваться чеклистом «всё зелёное»** — критичны операции: кто имеет SSH, где лежат бэкапы, когда последний restore-test.

**Приоритеты на ближайшие циклы (без фанатизма):**

1. Жёсткий пароль Grafana / ограничение доступа к портам мониторинга (firewall / bind / reverse proxy).  
2. Политика бэкапов: шифрование или зашифрованный носитель + проверка восстановления по расписанию.  
3. `.env.example` + защита от коммита секретов.  
4. Периодический dependency audit и ужесточение CI «красный = не мержим».  
5. По бюджету: второй узел Swarm / реплики stateless, отдельно — стратегия Mongo (replica set или managed).

## IV. Политика (нормативная часть)

### 1. Область и цели

- **Область:** платформа LGDX (server, client, микросервисы) в Docker Swarm.  
- **Цели:** конфиденциальность данных и платежей, целостность, доступность, снижение поверхности атаки, готовность к инцидентам.

### 2. Модель

- Наименьшие привилегии для сервисов, секретов, учёток.  
- Defense in depth: Nginx + приложение + ограничения контейнеров + секреты.  
- По возможности **fail closed**.

### 3. Секреты и ротация

- **Хранение:** в production — Docker Secrets; не вшивать в образы; не класть в git.  
- **Передача:** файлы в контейнере, поддержка `*_FILE` на сервере.  
- **Неисчерпываемый список:** JWT, admin key, Mongo/Redis/RabbitMQ, Stripe, SMTP, Twilio, Telegram-боты, Sentry/GA для клиента (часть через секреты в compose).  
- **Ротация (ориентир):** JWT ~90 дней с grace; admin ~180 дней; БД ~180–365; Stripe webhook при компрометации или ~180 дней.  
- **Процедуры:** `info/03_Production_Deployment.md`.

### 4. Логи и PII

- Не логировать сырые токены, пароли, полные PAN; маскировать email/телефоны где уместно.  
- Prod: `LOG_LEVEL=info`.  
- Stripe: в логах — идентификаторы намерений и статусы, не данные карты.

### 5. Аутентификация и сессии

- JWT + revocation в Redis; cookie HttpOnly; `COOKIE_SECURE=true` в prod.  
- Импersonation только для ролей с жёсткой серверной проверкой.

### 6. Rate limiting и злоупотребления

- Nginx: лимиты на API, login, register, верификацию почты, upload (см. `info/05_Nginx_Configuration.md`).  
- Сервер: `express-rate-limit` на чувствительных маршрутах.

### 7. Заголовки и CSP

- Nginx + Helmet; в prod `CSP_ENFORCE=true`; отчёты о нарушениях CSP — для разбора, не для игнорирования.

### 8. SSRF и внешние вызовы

- Тесты SSRF; allow-list исходящих; таймауты и backoff.

### 9. Файлы и загрузки

- Проверка типа/размера; лимиты строк для импорта; блокировка multipart вне разрешённых путей.  
- Prod: `PUBLIC_UPLOADS_ENABLED=false`.

### 10. Инфраструктура

- Внутренние БД/очереди без публикации портов наружу в secure-конфиге.  
- TLS 1.2+, редирект HTTP→HTTPS.  
- Сервисы расчёта цен/кэша — только overlay-сеть, не наружу.

### 11. Клиент (React)

- Sentry/sourcemaps через секреты; без небезопасных inline-скриптов в конфликте с CSP.

### 12. Зависимости

- Lockfile; `npm audit` в CI на `main` с порогом; план обновлений после тестов.

### 13. Бэкапы

- Расписание и retention — `backup-service`; отчёты в `file-processing/reports` с отдельной политикой retention (см. переменные `REPORTS_*` в compose).  
- Рекомендуется **периодический тест восстановления** в изолированной среде.

### 14. Мониторинг и инциденты

- Стек: Prometheus, Grafana, Loki, Alertmanager, экспортеры (детали — `info/18_Monitoring.md`).  
- Эскалация: L1 логи/health → L2 метрики/дашборды → L3 код/секреты/сеть.

### 15. Тестирование безопасности

- Автотесты в `server/src/tests/security/` (CSP/CORS/CSRF, SSRF, zip-bomb, multipart, файлы, rate limits).  
- Перед prod: осмысленный прогон тестов сервера согласно вашему стандарту релиза.

## V. Чеклист администратора (production)

- [ ] Сервисы здоровы, health проходят.  
- [ ] `NODE_ENV=production`, `COOKIE_SECURE=true`, `CSP_ENFORCE=true`.  
- [ ] Секреты Swarm актуальны, нет «забытых» монтирований.  
- [ ] TLS валиден, HSTS включён.  
- [ ] Логи без утечек секретов; уровень не debug.  
- [ ] `npm audit` / принятые риски задокументированы.  
- [ ] Бэкап БД успешен по расписанию; **restore-test** не старше политики.  
- [ ] Grafana: не дефолтный пароль; доступ ограничен.  
- [ ] Алерты доставляются и не игнорируются месяцами.
