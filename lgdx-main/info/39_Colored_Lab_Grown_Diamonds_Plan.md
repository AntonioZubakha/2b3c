# Цветные лабгроун бриллианты (Fancy Color) — план поддержки

**Дата:** 2025-02-20  
**Цель:** Определить, что нужно изменить в проекте LGDX, чтобы система работала с **цветными** лабгроун бриллиантами (Fancy Yellow, Fancy Pink, Fancy Blue и т.д.), а не только с белыми/бесцветными (D–G).

---

## Текущее состояние

### Что уже есть

- **Модель продукта** (`Product`): поля `color`, `overtone`, `intensity`, `stoneType`, `technology` — хранение цветных камней уже предусмотрено.
- **Импорт**: в `COLUMN_MAPPINGS` есть маппинги для fancy color (`FColor`, `fancy_color`, `Fancy Color`, `overtone`, `intensity`).
- **Маркетплейс**: фильтры по `color`, `technology`; эндпоинт `GET /colors` возвращает уникальные значения из БД (но валидация и UI ограничены D–G).
- **Клиент**: типы `DiamondBase` содержат `color`; в локалях есть `overtone`, `intensity`.

### Где сейчас только белые (D–G)

| Компонент | Ограничение |
|-----------|-------------|
| **api-product-sync-service** | `validateDiamondColor()` — только D, E, F, G. Иначе продукт **пропускается** (`skippedInvalidColor`). |
| **file-product-import-service** | Тот же `validateDiamondColor` в shared `productUtils` — цветные при импорте из файла **отклоняются**. |
| **server** (`productUtils`, inventory) | `validateDiamondColor()` — только D–G; при ручном импорте/обработке цветные не проходят валидацию. |
| **market-price-calculator-service** | `ColorCategoryEnum`: только D, E, F, G. `determineColorCategory()` для H, I, J, K и fancy возвращает `null` → продукт **не попадает** в категории и **не получает** `marketPricePerCarat`. |
| **ProductCategoryStats** (analytics, calculator) | Ключ категории: `shape-weight-clarity-color`; цвет — только D–G. |
| **Клиент (Catalog)** | `COLOR_OPTIONS = ['G','F','E','D']`; быстрый поиск и фильтры только по D–G; сообщения об ошибках: "Use D, E, F, or G". |
| **Category Stats / Analytics** | Запросы по `shape`, `weight`, `clarity`, `color` — цвет только D–G. |

Итог: цветные лабгроун бриллианты сейчас **не импортируются** (отсекаются при синхе/импорте), не получают рыночную цену и не поддерживаются в фильтрах и аналитике каталога.

---

## Что нужно для поддержки цветных лабгроун

### 1. Модель данных и импорт/синхронизация

- **Разделение «белый» vs «фенси»**  
  - Вариант A: считать цвет «фенси», если в `color` не одна буква D–Z (например, не входит в белый ряд D–G или явно есть подстрока типа "Fancy", "Yellow", "Pink").  
  - Вариант B: ввести флаг `isFancyColor: boolean` или тип `colorType: 'white' | 'fancy'` и заполнять при импорте.
- **Валидация цвета**  
  - Расширить `validateDiamondColor()` (server, api-product-sync, file-product-import): для **белых** оставить D–G (и при желании H–Z); для **фенси** — принимать значения вроде `Fancy Yellow`, `Fancy Intense Pink`, `Fancy Vivid Blue` и т.д. (список или паттерн + нормализация).  
  - Не отбрасывать продукт при «фенси» цвете: сохранять `color` (+ при наличии `overtone`, `intensity`) и помечать как фенси.
- **Импорт**  
  - В `processProduct` (и аналогах): если цвет — фенси, не вызывать `validateDiamondColor` в режиме «только D–G», а сохранять как есть и при необходимости заполнять `overtone`/`intensity` из маппингов.

Итог: цветные камни должны **проходить** импорт/синх и сохраняться в БД с корректными `color`/`overtone`/`intensity`.

---

### 2. Рыночная цена и категории (market-price-calculator-service)

Сейчас рыночная цена считается только для комбинаций shape + weight + clarity + **color (D–G)**.

- **Вариант A — отдельный контур для фенси**  
  - Определять «фенси» по полю цвета (или по `isFancyColor`).  
  - Для фенси не требовать категорию D–G; ввести отдельные категории, например:  
    - цвет фенси: `Fancy Yellow`, `Fancy Pink`, … (или группировка по основному цвету);  
    - при необходимости: интенсивность (Fancy / Fancy Intense / Fancy Vivid и т.д.).  
  - Ключ категории для фенси: например `shape-weight-clarity-fancyColor` или `shape-weight-clarity-fancyColor-intensity`.  
  - Расчёт `marketPricePerCarat` для этих категорий: отдельная логика (меньше данных → возможно только среднее по категории или копирование price поставщика до накопления статистики).
- **Вариант B — без рыночной цены для фенси на первом этапе**  
  - Цветные камни не включать в текущий пайплайн калькулятора; не писать им `marketPricePerCarat` (или подставлять `marketPrice = price` только для отображения).  
  - Позже добавить отдельный контур расчёта, как в варианте A.

Необходимо:  
- в `market-price-calculator-service` различать белый (D–G) и фенси;  
- для белых оставить текущую логику;  
- для фенси либо добавить новые категории и расчёт, либо явно не трогать `marketPricePerCarat` и описать это в коде/конфиге.

---

### 3. ProductCategoryStats и аналитика

- **Ключ категории** сейчас: `shape-weight-clarity-color` (color = D–G).  
- Для фенси: либо расширить ключ (например, `color` = код фенси + интенсивность), либо ввести отдельную «линейку» категорий для фенси и писать их в ту же коллекцию с другим форматом `color` (например, `FANCY_YELLOW`, `FANCY_PINK`).  
- API и агрегации по категориям (category-stats, дашборды): поддержать запросы по фенси-цвету и отдавать данные только по белым или только по фенси в зависимости от фильтра.

---

### 4. API маркетплейса и фильтры

- **GET /products (каталог)**  
  - Уже фильтрует по `color` через `normalizeColor`; если в БД появятся значения вроде "Fancy Yellow", их нужно поддерживать в фильтре (например, `color=Fancy Yellow` или кодированное значение).  
  - Не ограничивать валидацию схемы только D–G (если где-то есть enum по цвету — расширить или сделать строкой).
- **GET /colors**  
  - Уже возвращает `Product.distinct('color')`; после появления цветных камней в БД фенси цвета начнут появляться в списке. При необходимости — сортировка: сначала D–G, потом фенси.
- **Валидация запросов**  
  - В `ProductFilterSchema` и в контроллере: разрешить любые значения `color`, приходящие из справочника/фильтра, а не только D–G.

---

### 5. Клиент (каталог, карточка, аналитика)

- **Фильтры**  
  - Источник цветов: не хардкод `COLOR_OPTIONS = ['G','F','E','D']`, а загрузка с `GET /colors` (или комбинация: белые D–G + отдельный список фенси).  
  - В фильтре по цвету показывать и белые (D–G), и фенси (Fancy Yellow, Fancy Pink и т.д.), если они приходят с API.
- **Быстрый поиск**  
  - Сейчас парсинг только под D, E, F, G. Расширить: либо убрать проверку «только D–G» и принимать любой цвет из справочника, либо добавить отдельный формат запроса для фенси.
- **Карточка камня**  
  - Для фенси показывать `color` + при наличии `overtone`, `intensity` (уже есть в типах/локалях).
- **Страница аналитики по категориям**  
  - Выбор цвета: не только D–G, но и фенси, если по ним есть категории в ProductCategoryStats.  
  - Тексты типа "Market Analytics: {{shape}} {{weight}} {{clarity}} {{color}}" уже поддерживают подстановку; убедиться, что для фенси подписи адекватны (например, "Fancy Yellow" вместо одной буквы).
- **Локализация**  
  - Обновить сообщения вроде "Invalid color. Please use D, E, F, or G" — разрешить также фенси или заменить на "Use a valid color from the list".

---

### 6. Дополнительно

- **Определение «фенси» в одном месте**  
  - Вынести в shared утилиту: `isFancyColor(color: string): boolean` (и при необходимости нормализацию названия фенси), использовать в calculator, импорте и API.
- **Тесты**  
  - Добавить кейсы: импорт продукта с цветом Fancy Yellow / Fancy Pink; проверка, что продукт не отбрасывается и сохраняется с правильными полями.  
  - Проверка, что калькулятор не ломается при появлении в БД продуктов с фенси цветом (либо не назначает им категорию D–G, либо назначает фенси-категорию).
- **Документация**  
  - Обновить описание полей продукта (например, в `13_Database_Schema.md`): когда `color` — буква D–G, когда — строка фенси; описать использование `overtone` и `intensity` для фенси.

## Краткий чек-лист

| # | Задача | Где |
|---|--------|-----|
| 1 | Расширить/разделить валидацию цвета: белый (D–G) и фенси (принимать и сохранять) | server, api-product-sync, file-product-import `productUtils` |
| 2 | Не отбрасывать продукты с фенси цветом при импорте/синхе; заполнять color, overtone, intensity | processProduct в трёх сервисах |

## Выполнено (2025-02-20): приём цветных камней в БД

- **api-product-sync-service**: добавлены константы и хелперы (WHITE_COLOR_GRADES D–Z, isFancyColor, parseFancyColorString, normalizeWhiteColorRange); COLUMN_MAPPINGS: отдельный ключ `fancyColorValue` (FColor, fancy_color, Fancy Color, FancyColor); validateDiamondColor принимает белые D–Z и фенси; в processProduct — слияние color + fancyColorValue, для фенси заполняются color, intensity, overtone (в т.ч. парсинг из строки и из колонок).
- **file-product-import-service**: те же константы/хелперы, fancyColorValue в COLUMN_MAPPINGS и в NORMALIZED_FIELD_KEYS; та же логика слияния и обработки фенси; validateProductForApi разрешает фенси.
- **server** (productUtils): те же константы/хелперы, fancyColorValue в COLUMN_MAPPINGS; validateDiamondColor и processProduct обновлены по той же схеме; экспорт isFancyColor для использования в API/фильтрах.

Маркетпрайс для цветных пока не считается (калькулятор по-прежнему только D–G).
