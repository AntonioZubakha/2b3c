# Миграция пользователей и компаний (MySQL CSV → LGDX)

## Обзор

Перенос пользователей и компаний со старой площадки (MySQL, экспорт в CSV) на новую (MongoDB, Node/Express + React).

**Источники данных:**
- `users.csv` — пользователи (~15 066 строк)
- `companies.csv` — компании (~3 046 строк)
- `company_addresses.csv` — адреса компаний (~808 строк)

**Целевая платформа:** `server` (MongoDB, Mongoose) + `client` (React).

---

## 1. Сопоставление структур

### 1.1 Пользователи (users → User)

| Старая БД (CSV)     | Новая БД (MongoDB)     | Действие |
|---------------------|------------------------|----------|
| `id`                | —                      | Не хранить или только в `params`/отчёт для связи |
| `uuid`              | —                      | Опционально: сохранить в отдельное поле при необходимости глобального ID |
| `first_name`        | `firstName`            | Прямое |
| `last_name`         | `lastName`             | Прямое |
| `company_id`        | `company` (ObjectId)   | Маппинг по новой компании после миграции компаний |
| `email`             | `email`                | Прямое (unique, required) |
| `email_confirmed`   | `emailVerified`        | 1/"1" → true, иначе false |
| `phone`             | `phone`                | Прямое (required, unique) |
| `phone_cor` (confirmed) | `phoneVerified`  | Аналогично email |
| `disabled`          | `isActive`             | 1/"1" → false, 0/"0" → true (инвертировать) |
| `activated`         | Учитывать в `isActive` | Логика: активен если activated=1 и disabled=0 |
| `verified`          | —                      | Можно положить в доп. поле или не мигрировать |
| `role`              | `role`                 | **Маппинг** (см. ниже) |
| `country_id`       | —                      | В новой схеме User нет country_id; при необходимости — в `params` или отдельная коллекция |
| `params`            | —                      | Опционально: парсить JSON, сохранять язык и т.д. в профиль/настройки |
| `password` (hex)    | `password`             | Декодировать из hex в строку (это bcrypt-хеш от строки `plainPassword_salt`) |
| `salt`              | `legacyPasswordSalt`   | **Обязательно переносить.** На новом сайте при логине: если у юзера есть `legacyPasswordSalt`, проверка: `bcrypt.compare(enteredPassword + '_' + salt, user.password)`. После первого успешного входа пароль перехешируется в обычный bcrypt (без соли), поле очищается. |
| `modified` / `created` | `updatedAt` / `createdAt` | Unix → Date |
| `created_by`        | —                      | Опционально для аудита |

**Роли (старая → новая):**

- Старая: числа (например `1`, `2`, `2147483648`). Нужна таблица из старой БД (1=admin?, 2=?, 2147483648=supervisor?).
- Новая: `'admin' | 'supervisor' | 'manager' | 'logist' | 'buyer'`.
- Задача: составить маппинг (например по одному тестовому пользователю на каждую роль) и применить в скрипте.

**Ограничения новой схемы:**

- `email` и `phone` — **required** и **unique**.
- Пользователи без email или без phone: либо пропуск, либо заглушки (уникальные), с последующим исправлением/рассылкой.

**Пароли (старый сайт):**

- На старом сайте: хранятся `password` и `salt`. Проверка: строка `введённый_пароль_salt` (конкатенация через `_`), от неё берётся bcrypt-хеш и сравнивается с полем `password`.
- В CSV: `password` может быть в виде **hex-encoded строки** (декодировать в UTF-8 и сохранять как есть). Поле `salt` переносить в `legacyPasswordSalt`.
- На новом сайте реализована **legacy-проверка**: при логине если у пользователя задано `legacyPasswordSalt`, используется проверка `bcrypt.compare(enteredPassword + '_' + legacyPasswordSalt, user.password)`. После первого успешного входа пароль переводится в обычный bcrypt (без соли), `legacyPasswordSalt` очищается.
- Пустой пароль в CSV: выставить временный хеш + флаг сброса или не мигрировать и разослать восстановление пароля.

### 1.2 Компании (companies → Company)

| Старая БД (CSV)        | Новая БД (Company)        | Действие |
|------------------------|----------------------------|----------|
| `id`                   | —                          | Использовать только для маппинга company_id у пользователей |
| `uuid`                 | —                          | По необходимости |
| `name`                 | `name`                     | Прямое (unique) |
| `legal_address` (JSON) | `details.legalAddress`     | Парсить JSON, маппинг полей (countryId→country, cityName→city и т.д.) |
| `actual_address` (JSON)| `details.actualAddress`    | Аналогично |
| Банк, налоги, контакты | `details.bankInformation`, `details.taxInformation`, `details.phone`/`email` | Парсить из соответствующих колонок/JSON |
| `phone`, `email`       | `details.phone`, `details.email` | Прямое |
| `full_info`            | `description`              | Прямое |
| `tax_identity`         | `details.taxInformation.taxId` | Прямое |
| `role` (seller/buyer)  | `roles` (CompanyRole[])    | Маппинг seller→seller, buyer→buyer |
| `disabled`             | `status`                   | disabled=1 → suspended/rejected, иначе active/pending_review |
| `created` / `modified` | `createdAt` / `updatedAt`   | Unix → Date |
| Stripe-поля            | При наличии в новой схеме | Перенос по необходимости |
| FTP (params и т.д.)    | `ftpConfig`               | При наличии — маппинг |

**Адреса из company_addresses:**

- Одна компания (company_id) может иметь несколько адресов.
- В новой схеме: `details.legalAddress`, `details.actualAddress`, `details.shippingAddress`.
- Логика: например, адрес с `is_main=1` → legal или actual; остальные — в массив или в shipping. Нужно зафиксировать правило (один основной → legal, второй при наличии → actual, остальные → shipping или массив).

---

### 1.3 Связь пользователь ↔ компания

- Сначала мигрировать **компании**; при создании сохранять маппинг `old_company_id → new ObjectId`.
- При миграции **пользователей** подставлять `company = mapCompanyId[user.company_id]`.
- После создания пользователей обновить у каждой компании поле `users[]` (user, role, isActive) в соответствии с новой схемой Company.

## 2. Риски и ограничения

1. **Дубликаты email/phone** — в старой БД unique мог быть не везде. Нужна предобработка: дедупличение, решение кого оставить, кого пометить для ручной проверки.
2. **Пустые email/phone** — на новой платформе они обязательны. Варианты: не переносить таких пользователей или вводить уникальные заглушки и потом править.
3. **Роли** — без точной таблицы ролей старой БД маппинг будет эвристическим; лучше уточнить по старому коду/БД.
4. **Пароли** — только если формат действительно bcrypt в hex; иначе нужен отдельный слой проверки старого формата или принудительный сброс паролей.
5. **Справочники** — country_id, region_id, city_id в старой БД: если на новой платформе используются строковые коды (например US, IN), нужен справочник соответствия старых id → коды/названия.

## 5. Порядок выполнения (кратко)

## 6. Реализовано

- **Проверка паролей со старого сайта**  
  На новом сайте при логине: если у пользователя задано поле `legacyPasswordSalt`, проверка выполняется как `bcrypt.compare(enteredPassword + '_' + legacyPasswordSalt, user.password)`. После первого успешного входа пароль переводится в обычный bcrypt (без соли), поле `legacyPasswordSalt` очищается. См. `server/src/models/User.ts` (поле `legacyPasswordSalt`), `server/src/services/userService.ts` (логин).

- **Скрипт миграции**  
  `server/src/scripts/migrateUsersCompanies.ts` — читает `users.csv`, `companies.csv`, `company_addresses.csv` из папки `MIGRATION_CSV_DIR` (по умолчанию текущая директория), создаёт компании, затем пользователей с полями `password` (hex → строка) и `legacyPasswordSalt` = salt. Реализовано: маппинг ролей пользователя (в т.ч. 5→buyer, 23→logist, 2147483648→supervisor + isLgdealSupervisor), колонка `phone_confirmed`, correspondent bank и FTP из params для компаний, справочник country_id→код для адресов, BOM в CSV, итоговый отчёт.

  Запуск из папки `server`:
  ```bash
  MIGRATION_CSV_DIR=e:\LGDX npm run migrate-users-companies
  ```
  Сухой прогон (без записи в БД, без подключения к MongoDB):
  ```bash
  MIGRATION_CSV_DIR=e:\LGDX DRY_RUN=1 npm run migrate-users-companies
  ```
  Или с корня репозитория:
  ```bash
  MIGRATION_CSV_DIR=e:\LGDX npx ts-node -r tsconfig-paths/register server/src/scripts/migrateUsersCompanies.ts
  ```
  Переменные: `MIGRATION_CSV_DIR`, `MONGODB_URI` / `MONGODB_URI_FILE`, `DRY_RUN=1` (только разбор CSV, без записи в БД и без подключения к MongoDB).
