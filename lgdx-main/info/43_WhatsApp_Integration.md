# Архитектура и интеграция WhatsApp (Marketing Bot) в LGDX

В проекте LGDX реализована продвинутая интеграция с WhatsApp для маркетингового ассистента на базе LLM. Интеграция поддерживает сразу **два канала** работы параллельно:
1. **Cloud API (Meta)** — официальный, через webhooks.
2. **Baileys** — неофициальный WhatsApp Web протокол через сканирование QR-кода.

Оба канала сводятся к единому интерфейсу в Админ-панели и используют общую логику автоответов и очередей в Redis/RabbitMQ.

---

## 1. Общая архитектура и Микросервисы

- **`lgdx-server` (API)**: 
  - Принимает Webhooks от Meta (верификация по `GET`, приём событий по `POST`). Способен сам отправлять исходящие сообщения через Graph API.
  - Предоставляет админ-пулы: `/api/admin/whatsapp/...` (список чатов, переключение режима, генерация QR для Baileys).
- **`whatsapp-worker` (Cloud)**:
  - Docker-сервис с 1 репликой. Слушает очередь `whatsapp_incoming_tasks` в **RabbitMQ**. При получении сообщения обращается к LLM (OpenRouter) и отправляет ответ в Meta Cloud API.
- **`whatsapp-baileys-worker`**:
  - Docker-сервис с 1 репликой, поднимающий сессию WhatsApp Web через библиотеку Baileys. Сам слушает входящие сообщения (без RabbitMQ) и обрабатывает их через общий Job Processor.

---

## 2. Глобальный Автоответчик и Job Processor

Обработка всех текстовых сообщений проходит через единую точку — `processWhatsAppIncomingJob` (`server/src/whatsapp/whatsappJob.processor.ts`).
В системе есть режим **Глобального автоответа**:
- `off`: Бот выключен.
- `cloud`: На сообщения отвечает только Cloud API.
- `baileys`: На сообщения отвечает только сессия Baileys.

Если глобальный режим включен для канала, в который пришло сообщение:
1. Проверяется флаг **AI Paused** (Пауза для конкретного чата).
2. **Отправка "Прочитано"**: Если ИИ собирается ответить, бот сначала сигнализирует приложению клиента, что сообщение прочитано (синие галочки). Для Cloud используется Graph API (`status: read`), для Baileys — `sock.readMessages()`, проброшенный через `whatsappOutbound.service`.
3. Собирается история переписки, вызывается OpenRouter.
4. Отправляется ответ клиенту. Сохраняются состояния.

## 3. Маппинг контактов и связь с БД Пользователей

WhatsApp Meta Graph API и Baileys могут использовать обфусцированные ID вида `lid_...` для защиты приватности. В LGDX реализован сложный механизм нормализации и поиска связей этих номеров с зарегистрированными пользователями базы данных:

1. **Redis LID Mapping**: Сокет Baileys при получении данных о контакте сохраняет привязку между обфусцированным `lid` и реальным номером телефона в Redis (`whatsapp:baileys:lid_pn:*`).
2. **MongoDB Регистрация**: В контроллере админки `adminWhatsAppController.ts` происходит агрегация:
   - Если номер телефона пришел как `lid_...`, он расшифровывается через `mget` в Redis.
   - Очищенные от всех спецсимволов цифры собираются в массив.
3. **Безошибочный Джоин в БД**: Для поиска используется массив динамических регулярных выражений: `^\+?1\D*5\D*1...` в MongoDB. Это значит, что если клиент указал телефон с пробелами, тире или скобками (`+1-515-(123)`), запрос **безошибочно** найдет этого пользователя, игнорируя спецсимволы.
4. В **Админ-панели** вместо сырых номеров и LID-кодов выводится дружелюбный формат `Имя Фамилия (Компания)`. Либо `+Телефон`, если пользователь не найден, либо грациозный fallback `Hidden Number (LID)`.

---

## 4. Хранение данных (Redis)

Все актуальные переписки и статусы лежат в Redis:
- `whatsapp:chat:{cloud|baileys}:{waId}` — Sorted set (история сообщений).
- `whatsapp:ai_paused:{cloud|baileys}:{waId}` — Флаг паузы LLM для чата.
- `whatsapp:baileys:outbound` — Очередь ручных ответов из админки для Baileys-воркера.
- `whatsapp:baileys:connection` / `whatsapp:baileys:qr` — Состояние сессии Baileys.

---

## 5. Админ-панель (UI)

Место: `client/src/components/Admin/WhatsAppManagement.tsx`.
Возможности:
1. Выбор глобального режима.
2. Просмотр склеенной (`Merged`) истории переписки из двух источников по одному и тому же номеру.
3. Выключение ИИ (переход к ручному общению оператора).
4. Ручная отправка текстовых сообщений из админки (через Graph API или Baileys `RPUSH`).
5. Сканирование QR-кода прямо на странице для авторизации сессии Baileys.

---

## 6. Docker и Секреты (production)

Для запуска необходимы внешние секреты (Docker Swarm Secrets):
- `WHATSAPP_ENABLED` / `WHATSAPP_BAILEYS_ENABLED`
- `WHATSAPP_VERIFY_TOKEN`
- `WHATSAPP_ACCESS_TOKEN`
- `WHATSAPP_PHONE_NUMBER_ID`
- Конфигурации для MQ и Redis (`RABBITMQ_URL`, `REDIS_URL`).

Для Baileys сессии монтируется отдельный `volume`: `whatsapp_baileys_data`, чтобы при перезапуске контейнера сессия WhatsApp Web не сбрасывалась.

---

## 7. Риски и Ограничения
- Сообщения из Cloud API могут возвращать ошибку 400, если пытаться отправить произвольный текст вне разрешенного **24-часового окна клиентского обращения** (мета-политика). В этом случае первые сообщения должны быть шаблонными (Message Templates, настраиваются в кабинете Meta).
- Baileys не является официальным API WhatsApp, в случае жесткого спама номер-донор может быть заблокирован алгоритмами Meta (использовать только для мягкого маркетинга).
